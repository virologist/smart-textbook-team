# H 框架对照审计（smart-textbook-team ↔ H=(E,T,C,S,L,V)+P）

> **这份文件解决什么问题**：本包与 `agent-harness-expert` 专家团各有一套 harness 术语，
> 长期**不同源**——本包说「13 态 / 五档预算 / E 码 / 门禁 4」，H 框架说「E/T/C/S/L/V + P」。
> 两套体系描述的是同一类东西，却互相无法引用：读本包的人不知道哪层是 V，
> 读 H 框架的人不知道「门禁 4」属于哪层。本文件做**概念映射 + 覆盖度审计**，
> 目的有两个：① 让两套体系可互相引用；② 用 H 框架的「必答设计问题」反查本包的真实缺口。
>
> **权威源**：H 六层定义见 `agent-harness-expert/skills/agent-harness-architect/references/h-framework.md`
> （E 执行循环 / T 工具注册 / C 上下文管理 / S 状态存储 / L 生命周期钩子 / V 评估接口；P 架构范式）。
> 本文件只做映射，不复述定义、不改写 H 框架。

## 二、本包独有概念 → 归入哪一层

这些概念在 H 框架里没有专名，但对号入座后才能被外部理解：

| 本包概念 | 含义 | 归入 | 说明 |
|---|---|---|---|
| **五档 token 预算 + 80% 降级** | `budget.tokens_used / tokens_limit`，超 80% 触发降级策略 | E | E 层「防跑飞」三保险（轮次/预算/超时）的预算那一条 |
| **E1–E5 错误严重分级** | 错误按严重度分级处置（重试/降级/上报/停机） | E | E 层「失败怎么回喂」的**分类恢复表** |
| **打回计数防逃逸** | 计数键 = `correlation_id + 问题指纹`，跨 task_id 累计，≥2 强制介入 | E | 防「改 task_id 洗计数」——H 框架「原地打转识别」的一种具体检测器 |
| **门禁 4 判据族（4.0–4.13c）** | 交付前的机械校验：结构/数据/引用/术语/修订态/溯源 | V | V 层「终止条件谁说了算」的答案：**确定性代码说了算**，不是模型自评 |
| **R5 五维质量评分（80 分红线）** | 知识严谨 30% / 前沿 15% / 易懂 25% / 职教适配 20% / 规范 10% | V | 语义级评估，与机械判据并列为双轨 |
| **职责隔离（writer ≠ examiner）** | 写稿的与判稿的必须是不同 agent | P + V | P 层编排约束，V 层独立性前提 |
| **路径所有权表** | 每个产物只有一个合法写者 | L + C | 生命周期内的写权限边界 |

## 三、用 H 框架反查本包缺口（审计结论）

拿 H 框架每层的「必答设计问题」逐条问本包，**问出 3 个真缺口**（已登记，均非本轮修复项）：

1. **E 层「墙钟预算与并行」未设计**：本包有 token 预算，但**没有一轮的墙钟时间预算**，
   也没有声明「哪些成员调用可并行」（实际全靠主理人临场判断）。文献检索理论上可按缺口
   清单 fan-out 并行（`literature-scout` 输入契约已写「可并行 ≤5 分支」），但**没有并行度上限的判据**。
2. **C 层无「上下文压缩/蒸馏」策略**：本包靠「信封只传引用（`context_refs`）+ 成员按需 Read」
   控制上下文，但没有**压缩**机制——长章（>15 条引用）时 examiner 的 R3 靠「分批 + 落盘断点续跑」
   绕开上下文上限，属于工程规避而非上下文管理设计。
3. **L 层无运行时钩子（pre/post hook）**：本包的「生命周期」是**流程级**（13 态顺序）而非
   **事件级**（工具调用前后、成员 spawn 前后）。`install.sh` 只是安装期钩子。
   影响：无法在「成员即将写文件」这类瞬时事件上做拦截，只能靠事后门禁（V 层兜底）。

## 四、本包对 H 框架的补充（内容生产域实践）

H 框架是通用骨架，本包在「长链路内容生产」这个域里补了三条可复用的具体做法：

1. **机械判据与语义判据双轨**：V 层若只有 LLM 自评（语义），容易被"看起来合理"骗过；
   若只有脚本（机械），抓不到深度/风格。本包把 V 拆成「门禁 4 机械族 + R1–R5 语义轮」，
   并规定**机械层不过不许进语义层**（fail 一律回 PRODUCE）——这是可移植的门禁顺序原则。
2. **判据表 ↔ 实现 ↔ 契约三方断言**：本包用 `tests/test_smart_textbook_team.py` 的 F37 组
   静态断言「判据表里每个 ID 在脚本里有 `r.add()`」，专治「规范声称超出实现能力」
   （本包历史上 4.10–4.12 曾整族零实现，判据表却写着"已有"）。任何"声称有校验"的体系都该加这条。
3. **降级必留痕**：环境不具备时（如 nbconvert 缺失）允许降级，但降级原因必须写进判据 detail
   （`4.10e` 会输出「降级直执行通过（nbconvert 不可用）」），**不允许静默等价**。
   这让"通过"这个词在不同环境下的可信度是可审计的。

## 五、维护约定

- 新增 H 层相关机制时，**同时更新本文件对应行**（否则又变成"两套术语互不相认"）。
- 本文件不做权威定义，只做映射；H 框架定义变更 → 以 `h-framework.md` 为准，本文件跟随修订。
- 覆盖度标记：✅ 覆盖 / 🟡 部分 / ❌ 未覆盖。任何 🟡/❌ 都必须在 §三 有对应的缺口条目。
